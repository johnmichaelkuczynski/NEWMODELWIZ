NON-NEGOTIABLE REQUIREMENTS (read first)
These are the parts a previous synthetic-user build for a different app failed on. If any are missing, the deliverable is rejected.

No green-checkmark theater. R1 produces raw evidence, not "PASS." Exact text typed, exact text returned, exact network responses, exact screenshots. Judge produces prose critique, not booleans. PASS/FAIL exists only as a filter for failures.md — never as a substitute for evidence.
The HTML report must be reviewable in under 30 minutes. Every interaction shows step + R1's input verbatim + app's response body + screenshots + judge critique. No collapsed sections.
The live view must show R1's actual inputs and the app's actual outputs as they happen — not "Step 4 of N in progress." Spec below.
Network traffic captured raw. Every /api/* request and response body in network.log as JSONL.
Three screenshots per interactive step (before / after typing / after app responds). Navigation-only steps get one. The sanity check distinguishes the two cases.
If R1 cannot complete a step, the failure is logged with the actual error, page HTML at moment of failure, and a screenshot. No skipping and marking green.
Per-step API-call expectations are route-specific. "Run Full Suite" expects a specific documented sequence of routes. Boolean checks forbidden.
Critical button clicks wrapped in Promise.all([page.waitForResponse(predicate), click]).

What's different about this app — Cognitive Analysis Platform's defining features
This is a serious analytical instrument, not a chat app. It scores texts on 17 cognitive dimensions, runs multi-LLM comparisons, and chains together a 4-stage Full Suite pipeline. Three things make it different from previous R1 targets:
It already has an auto-running 18-check diagnostic. R1 runs it as Function 1 and as a final check. The diagnostic itself is part of the test — R1 verifies the diagnostic page actually auto-runs without user action per blueprint.
It has explicit UI/UX invariants the user has set, not just functional ones. ZHI labels must not include parenthetical provider names. Error messages must be friendly (never raw "Error: 404 {...}"). Validation toasts must not block. These are testable.
The Full Suite pipeline is a 4-stage chain that is the app's flagship feature. R1 must run it end-to-end and verify all four stages fired in order.
The six invariants that elevate to CRITICAL VIOLATION status:
Invariant A — ZHI labels never include parenthetical provider names. Per blueprint UI label rule: "show 'ZHI 2', never 'ZHI 2 (Anthropic)'." R1 scans every page for any element containing the substring ZHI  (with space) immediately followed by parenthesized text. If any found, CRITICAL VIOLATION (user preference violation).
Invariant B — No raw error strings shown to the user. Per blueprint: "NEVER show raw error messages." R1 deliberately triggers error conditions (submit empty input, submit invalid provider, hit a known-failing endpoint with bad payload). Then R1 scans the visible UI text for raw-error patterns: substrings like Error:, 404, 500, Internal Server Error, at Object., at fetch, stack traces, {"error":. If any visible to user, CRITICAL VIOLATION.
Invariant C — Auto-fallback chain works when primary provider fails. Per blueprint: ZHI 5 → 2 → 1 → 3 → 4 fallback when 429/5xx/timeout. R1 cannot easily induce real failures, but R1 can verify the chain by:

Submitting an analysis with each provider explicitly selected
Verifying response actually uses that provider (or its documented fallback partner)
If ZHI 5 returns valid output for a request that's known to be cheap, the chain isn't being triggered
If the diagnostic ping shows a provider is unhealthy, R1 submits a request and verifies the response indicates fallback engaged (response time longer, response shape includes fallback metadata if implemented, or judge notices stylistic shift)
A provider configured as broken (env var missing per diagnostic) must NOT silently return Grok output without indicating fallback. If R1 selects "ZHI 4" with PERPLEXITY_API_KEY missing and gets a successful response without any fallback indication, JUDGE CONCERN (silent fallback is a UX issue).

Invariant D — Full Suite pipeline executes all 4 stages in order. Per blueprint: Stage 1 Batch (5 or 6 modes parallel) → Stage 2 BOTTOMLINE → Stage 3 Objections (25 + counter-arguments) → Stage 4 Refined Rewrite. R1 captures all network calls during a Full Suite run and verifies:

Multiple POST /api/text-model-validator/batch calls (one per mode, or one batch call — verify against actual implementation) fire FIRST
Then POST /api/text-model-validator/bottomline fires AFTER batch completes
Then POST /api/text-model-validator/objections fires AFTER bottomline completes
The "Download Everything as One Document" button appears at the end
The downloaded text contains content from all 4 stages

If stages fire out of order, are skipped, or the download is missing content, CRITICAL VIOLATION.
Invariant E — Diagnostic auto-runs on page load. Per blueprint: "useEffect auto-start." R1 navigates to /diagnostic and watches network traffic. Within 5 seconds, POST /api/diagnostic/run MUST fire without R1 clicking anything. If it doesn't, CRITICAL VIOLATION (the documented auto-run behavior is broken).
Invariant F — JMK admin bypass works without breaking normal flows. Per blueprint: JMKUCZYNSKI username = admin bypass, no password required. R1 tests both paths:

Register a non-JMK user. Verify password is required. Verify auth flows work normally.
Log out. Log in as "JMKUCZYNSKI" with no password / any password. Verify bypass works AND verify the non-JMK user (created earlier) is unaffected.
If JMK bypass fails OR if creating a JMK session somehow affects other users, CRITICAL VIOLATION.

Architecture

Browser automation: Playwright (Node, single-file tools/r1/run.mjs). Standalone Node project, not in any workspace.
R1's brain: Anthropic API. Model: claude-opus-4-7. Key in ANTHROPIC_API_KEY.
Judge: Separate Claude API call per interaction. Prose critique. For analytical-output quality, the judge gets the input + the scoring output and assesses whether the scores are defensible.
Live view: node:http server on port 7777. Zero extra deps.
Target app: Cognitive Analysis Platform running locally. Default APP_URL=http://localhost:5000. R1 registers a non-JMK user for normal flows, then also tests the JMK bypass.

Fixtures
R1 needs analytic-quality texts. Include in fixtures/:

high-quality-essay.txt — ~2000 words, dense intellectual content with clear argument structure (e.g., a philosophical essay on a non-obvious topic). For testing high-end scoring calibration.
mediocre-essay.txt — ~1000 words, surface-level treatment, padding, vague claims. For testing mid-range scoring.
shallow-text.txt — ~500 words, low-content / repetitive / hollow. For testing low-end scoring.
paired-texts/a.txt + paired-texts/b.txt — two related but distinguishable essays for comparison tests.
pdf-with-math.pdf — a PDF containing mathematical notation for OCR/parsing tests.
ai-generated-text.txt — text known to score high on GPTZero (R1 generates this from an LLM at startup if not present, saves to disk).

Use the feature with a fixture appropriate for it (happy path)

Use it with empty / malformed input to trigger errors (for Invariant B)

Edge cases (oversized input, special characters)
